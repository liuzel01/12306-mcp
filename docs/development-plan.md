# 12306-mcp 开发计划

## 目标

在不引入购票、登录和订单操作等重大功能的前提下，提升 12306 MCP 服务的稳定性、模型调用成功率、结果可用性和后续维护效率。

开发分支：`codex/12306-mcp-improvements`

基线：远端 `origin/main`

## 当前基线观察

- `src/index.ts` 当前同时负责上游请求、车站数据加载、解析、格式化、MCP 工具注册和进程启动。
- 启动阶段通过顶层异步初始化加载车站数据和查询路径；上游不可用时可能导致服务启动失败。
- `make12306Request` 当前将不同类型的请求失败统一转换为 `null`，调用方难以区分超时、网络错误和上游响应错误。
- 现有功能主要通过文本 JSON 返回，缺少统一的结构化结果约定。
- 当前没有独立的自动化测试目录；后续功能必须同步添加测试，不以人工调用作为唯一验收方式。

## 实施原则

1. 每项功能先补测试或测试夹具，再实现代码。
2. 不改变现有 MCP 工具名称和已有参数含义；如需不兼容变更，新增版本化接口。
3. 不保存或输出 Cookie、完整请求头等敏感信息。
4. 上游请求设置明确超时、有限重试和可识别错误码。
5. 保持 stdio 和 HTTP 两种 MCP 传输方式都能工作。
6. 默认不提交本地生成的权限变化；构建产物是否提交以仓库现有约定为准。

## 优先级与工作项

### P0：上游请求与启动稳定性

#### P0.1 统一请求层

- 为 12306 请求增加连接/响应超时。
- 对网络超时、连接错误和 5xx 做有限次数重试，并设置退避间隔。
- 定义统一的成功/失败结果类型，至少区分：参数错误、上游超时、上游不可用、响应解析失败和未知错误。
- 日志包含接口类别、耗时和错误类别，不包含 Cookie 或敏感请求头。
- 保持 MCP 返回内容对模型友好，明确提示是否可以重试。

#### P0.2 延迟初始化与缓存

- MCP 服务先完成启动，再按需初始化车站数据、余票查询路径和中转查询路径。
- 对车站数据和动态查询路径增加内存缓存及失效时间。
- 初始化失败时由对应工具返回可理解的错误，不使整个 MCP 进程无条件退出。
- 并发初始化只允许一个请求执行，其他请求复用同一个 Promise。

#### P0 测试与验收

- 使用 mock HTTP 客户端测试成功、超时、5xx、解析失败和重试次数上限。
- 测试上游不可用时 MCP 仍能启动，并能返回明确错误。
- 测试并发首次调用不会重复加载初始化资源。
- 保留 MCP `initialize`、`tools/list` 和基础工具调用的协议测试。

### P1：输入校验与结构化结果

#### P1.1 参数校验

- 日期校验同时检查格式和真实日期。
- `sortFlag`、`format` 等有限取值参数改用枚举约束。
- 校验出发时间不晚于到达时间，限制分页/返回数量，避免异常大结果。
- 统一处理车站名称中的“站”后缀、空格和大小写。

#### P1.2 结构化输出

- `get-tickets` 保留当前文本输出，同时提供稳定的结构化字段。
- 统一车次、出发时间、到达时间、历时、座位余票和查询时间字段命名。
- 空结果、部分字段缺失和上游异常使用统一响应结构。
- 保证 `text`、`csv`、`json` 三种输出格式的行为和文档一致。

#### P1 测试与验收

- 参数边界测试：非法日期、非法排序、负数、过大数量、时间范围错误。
- 解析 fixture 测试：正常车次、无票、无座、跨日到达、字段缺失和空结果。
- 结构化结果契约测试，确保字段名称和类型稳定。

### P1：车站搜索接口

新增 MCP 工具：`search-stations`

- 支持中文名称、简称和拼音的模糊匹配。
- 正确处理“北京”“北京站”“北京南站”等常见输入。
- 返回候选车站、城市、`station_code` 和匹配原因/排序。
- 设置最大候选数量，避免把完整车站表塞入模型上下文。
- 当存在多个候选时明确标记需要用户确认，避免静默选择错误车站。

测试要求：

- 精确匹配、后缀清理、模糊匹配、无结果、多候选和大小写测试。
- 使用固定车站 fixture，测试不依赖实时 12306 网络。
- 增加 MCP 工具 schema 和典型调用的契约测试。

### P2：服务状态接口

新增 MCP 工具：`get-service-status`

- 返回服务版本、初始化状态、缓存状态、最近上游检查结果和检查时间。
- 不返回 Cookie、内部网络地址或完整异常堆栈。
- 区分 MCP 服务正常、上游暂时不可用和初始化未完成。

测试要求：

- 覆盖启动未初始化、初始化成功、初始化失败、缓存命中和缓存过期。
- 验证敏感字段不会出现在返回结果和日志中。

### P2：小型相关接口扩展

在前述基础稳定后，按需求选择实现，不要求第一轮全部完成：

- `get-ticket-summary`：返回适合对话展示的精简车次摘要。
- `get-train-operating-days`：判断指定车次在指定日期是否运行。
- 增强 `get-train-route-stations`：补充停站时长、区间标记和是否停靠指定车站。
- `filter-tickets`：对已获取结果按时间、车次类型和座位可用性进行二次筛选。

每个新工具必须包含独立的输入 schema、错误行为说明、fixture 测试和至少一个 MCP 协议调用测试。

## 测试工程计划

建议新增：

```text
tests/
  fixtures/
    stations.ts
    tickets.ts
    routes.ts
  unit/
    station-search.test.ts
    date-validation.test.ts
    ticket-parser.test.ts
    request-client.test.ts
  integration/
    mcp-protocol.test.ts
    tool-contracts.test.ts
```

建议增加 TypeScript 测试运行器（例如 `tsx`）作为开发依赖，并补充 npm scripts：

```json
{
  "test": "npm run build && npm run test:unit && npm run test:integration",
  "test:unit": "tsx --test tests/unit/**/*.test.ts",
  "test:integration": "tsx --test tests/integration/**/*.test.ts",
  "test:mcp": "tsx --test tests/integration/mcp-protocol.test.ts"
}
```

如果最终采用其他 TypeScript 测试框架，应统一替换上述命令。CI 中执行构建、单元测试和 MCP 协议测试。实时 12306 查询只作为可选的 smoke test，不能作为默认 CI 测试依赖。

## 推荐提交顺序

1. 测试基础设施、fixture 和请求层错误类型。
2. P0 请求超时/重试、延迟初始化和缓存。
3. P1 参数校验与 `get-tickets` 结构化结果。
4. `search-stations` 及其测试。
5. `get-service-status` 及其测试。
6. 根据实际需求选择 P2 小接口扩展。

## 完成标准

- `npm run build` 成功。
- 自动化测试覆盖新增逻辑和主要错误路径。
- stdio 与 HTTP MCP 均可完成初始化、工具发现和基础工具调用。
- 上游超时或不可用时，服务不会无提示崩溃，模型能得到可操作的错误信息。
- 不影响既有工具名称、既有正常参数调用和当前本地启动方式。
- Git 工作区不包含未经确认的构建产物权限变化或调试文件。

## 非本阶段范围

- 12306 登录、验证码、下单、支付、抢票和订单管理。
- 保存用户身份信息或长期保存上游 Cookie。
- 大规模重写或更换 MCP SDK。
- 依赖实时网络的全量端到端测试。
